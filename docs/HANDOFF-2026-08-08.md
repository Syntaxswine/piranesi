## THE PRIORITIES — three ways the save system still loses work

All three were found by an adversarial pass over the working tree, **with the
suite green**, and all three were reproduced rather than reasoned about. They
are ranked by how much work goes.

### 1. Two tabs on the same building overwrite each other  ·  BACKLOG 0u

**What you see:** you build for an hour, click once in a stale tab you forgot
was open, and the building reverts to whatever that tab was holding.

**The mechanism.** Boot opens `SLOT || store.openName() || first.name`
(`game.js`), so two normally-opened tabs open the *same* building. Each holds
its own in-memory `World`; `save()` fires on every place and remove and writes
its own `toJSON()` over the shared key. Last click wins, and the loser was the
tab with the work in it.

**Why it is first:** drawing a block and then building with it is the normal
workflow, so `draw.html` and `index.html` are routinely open together and a
second game tab is one middle-click away. This is not an edge case, it is
Tuesday.

**Cheapest fix.** A token in the record. Each tab mints one on open and writes
it with every save; `saveBuilding` refuses if the stored token is not the one
this tab last wrote, and offers *save as* instead. Nothing needs locking and
nothing needs a server — it only has to notice.

### 2. The library is one key, so a quota failure freezes everything  ·  BACKLOG 0v

**What you see:** *"this browser is out of storage"* in the HUD, and then
nothing can be saved — including a brand-new building with one block in it.

**The mechanism.** `piranesi/buildings` holds the whole collection in one value,
so `setItem` must fit the entire array every time. Once it does not fit, no
building can be written, however small.

**Cheapest fix.** Per-building keys — `piranesi/building/<slug>` and an index —
which two of the three save designs called for and which fixes a second thing at
the same time: it shrinks the blast radius of a corrupt value from *the library*
to *one building*. Migration is the same read-once-and-keep pattern already in
`Store.migrateBuildings`.

### 3. Anchors are keyed by an index into a generated list  ·  BACKLOG 0w

**What you see:** nothing, until the day you retune the anchor sampler and every
torch in every save is on a different bracket.

**The mechanism.** `anchors.js` — `siteId = ${layer}|${x},${y},${z}#${i}`, where
`i` indexes a *seeded shuffle* inside `anchorsFor`. Position and recipe are
stable identities; `#i` is not. **This is the exact bug `recipe.js` was written
to kill, one level down** — and now that saves export and travel, it travels
with them.

**And the trap in fixing it,** which is why this is third and not first: the
obvious repair is to rewrite saved keys to geometry (`@side,u,z`) at load time,
and that migration is exact *only while the current sampler agrees with the old
one*. **A migration that silently moves every torch is worse than an index that
fails visibly.** Whatever is done here needs a way to check itself against a
committed corpus of saves first — of which there is currently one,
`docs/sample-save.json`, and it has no anchors set.

## Also open, but nobody loses anything

`0r` the kit spec's role filters cannot see the `D:` family, so `assemble.mjs`
cannot tile with a hand-drawn shelf. `0s` there is no undo in the game — now
that buildings are named and plural, "revert to last saved" is the cheap
version. `0t` a building's view is stored but not exported. `0p` the kit spec
has not been argued with since the vocabulary went from 15 words to 17, which is
what took it from 96/100 fully flush to 82/100. And a fourth, unrecorded until
now: **nothing distinguishes an older copy of a building from a newer one** — no
timestamps, no content identity — so a library of similar buildings is hazardous
to prune.

## The one lesson to carry

> The suite passed a test named *"storage that will not parse is reported and
> LEFT ALONE"* while a corrupt key was being destroyed by the next click.

The invariant the code **claimed** was *a key that will not read is never
written over*. The invariant it **tested** was *the reader does not delete it*.
Those differ by exactly the bug, and the test never wrote after the failed read.

**For any "we never lose X" comment, write the test as the whole sequence a
player performs — the failure is almost always one step after the one you
tested.** It is the same shape as this project's older law about numbers that
agree with everything, and it has now caught something in three consecutive
sessions.
